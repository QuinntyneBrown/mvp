.NET global tool

Start with the domain, not the plumbing.

mvp turns a small YAML manifest into a buildable full-stack starting point: a layered .NET 10 backend, an Angular 22 workspace, JWT authentication, and Playwright end-to-end tests. Generation is offline, deterministic, and transactional.

What you get

Layered .NET 10 backend

Domain, Application, Infrastructure, and API projects with a one-way dependency direction, MediatR handlers, FluentValidation, and EF Core.

JWT authentication

Register and sign-in endpoints, BCrypt hashing at work factor 12, bearer validation with issuer, audience, lifetime, and signing-key checks.

Angular 22 workspace

A standalone-component application plus api, components, and domain libraries wired through path aliases, with an auth guard and interceptor.

Playwright end-to-end tests

Page-object classes for every generated page and a working registration and sign-in journey.

Manifest-driven scaffolding

Declare entities, pages, and components in YAML. Each one expands into backend handlers, frontend routes, and test page objects.

Focused sub-generators

Eight incremental commands generate a single project — an API, a class library, an Angular app — when you don’t want the whole solution.

Read this before you install

Stable and prerelease builds

dotnet tool install -g Mvp.Cli installs the latest stable version. Every commit to main also publishes a prerelease, available with --prerelease. Prereleases pass the same test matrix but are not release-reviewed and can change between builds — see Installation.

How it works

Every run follows the same four steps, and nothing touches your filesystem until the first one passes:

  1. Load. The YAML manifest is read (1 MiB maximum) and deserialized into input objects. Unknown fields are reported as warnings, not failures.
  2. Validate. Names, routes, property types, duplicates, reserved words, and the output path are checked in aggregate — you get every problem at once, not the first one.
  3. Render. Templates embedded in the tool are rendered into a uniquely named staging directory beside the target. No network access is required at any point.
  4. Publish. The staging directory is moved into place atomically. An existing target is a conflict unless you pass --force, which replaces it through a recoverable backup.

See Output safety for the staging, backup, and rollback details, and Errors & exit codes for what each failure looks like.
