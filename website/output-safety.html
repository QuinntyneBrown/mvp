Output safety

A code generator that half-writes a tree is worse than one that refuses to run. Every mvp command either produces a complete result or leaves your filesystem exactly as it found it.

The order of operations

  1. Load the manifest, if one was given.
  2. Validate everything — names, routes, types, duplicates, reserved words, and the resolved output path.
  3. Create parent directories, but only now, after validation passed.
  4. Check for a conflict. If the target exists and --force was not given, stop with exit code 2.
  5. Render every file into a uniquely named staging directory beside the target.
  6. Publish by moving the staging directory into place.
Nothing is written before step 3

An invalid name produces no directory at all — not an empty one, not a partial one. You can safely re-run a failed command after fixing the manifest.

Staging and publication

Rendering never targets the final path. The tool creates two possible siblings of the target, both hidden by a leading dot and suffixed with a fresh identifier so concurrent runs cannot collide:

alongside the target
out/
├── Acme                                  ← the target
├── .Acme.mvp-stage-<32 hex characters>   ← rendered here first
└── .Acme.mvp-backup-<32 hex characters>  ← only when --force replaces something

Because staging is a sibling rather than a temp-directory copy, publication is a move within one filesystem — fast, and atomic as far as the operating system allows. The staging directory is removed in a finally block whether the run succeeds, fails, or is cancelled.

Conflicts are explicit

An existing target is never silently overwritten and never merged into.

exit code 2
Generating dotnet-angular-jwt-mvp...
The target '/work/out/Acme' already exists. Re-run with --force to replace it safely.

This makes the tool safe to put in a script: a conflict is a distinct exit code you can branch on, not an ambiguous failure.

--force and rollback

When you do pass --force, replacement runs as a sequence that can be undone:

  1. Render the new tree into staging.
  2. Move the existing target aside into the backup directory.
  3. Move staging into the target position.
  4. Delete the backup.

If step 3 fails, the backup is moved back and the original exception is rethrown — you end up with the tree you started with. If only step 4 fails, generation has already succeeded, so it is reported as a warning rather than an error:

exit code 0
Generating dotnet-angular-jwt-mvp...
Generated 102 files at '/work/out/Acme'.
Replaced the existing target '/work/out/Acme' using transactional backup and rollback.
warning: Generation succeeded, but backup cleanup failed: <reason>
Recoverable is not the same as non-destructive

The rollback protects you from a failed replacement. A successful one replaces the entire target directory, and anything you wrote inside it is gone. Generate into a new directory and merge your changes across.

Path containment

Manifest values reach the filesystem as directory and file names, so every write is re-resolved against the target root and rejected if it escapes:

Template output path '<path>' escapes the target directory.

Names are validated as PascalCase identifiers long before this point, so --name ../Escape fails at validation. Containment is the second line of defence — it holds even if a template is wrong.

exit code 1 — nothing created
$ mvp new core --name ../Escape --output ./out
Generating core...
Input validation failed:
- Name '../Escape' must be a PascalCase identifier containing only ASCII letters and digits.

The same principle applies to the one external process the tool can start: arguments for --use-angular-cli are passed as a list, never as a concatenated command string, so no manifest value can inject an argument.

File encoding

PropertyAlways
EncodingUTF-8 with no byte-order mark
Line endingsLF, normalized from any CRLF in the templates
PathsRelative, forward-slash separated, ordinal-sorted in the result

This holds on every platform, so a solution generated on Windows and one generated on Linux are byte-identical and produce no line-ending noise in version control.

Determinism

The same manifest always produces the same bytes — no timestamps, no ordering by filesystem enumeration, no random identifiers inside generated content. This is asserted in the test suite by generating twice into separate workspaces and comparing file by file, which makes template changes visible in review instead of showing up as noise.

Cancellation

Press Ctrl+C and the run stops cleanly:

exit code 130
Generation cancelled.
  • The staging directory is deleted.
  • The target is untouched — it is only ever created by the final move.
  • If --use-angular-cli had started a child process, the whole process tree is killed and awaited rather than orphaned.

Offline by construction

Templates are embedded resources inside the tool. Generation makes no network requests and restores no packages — the generated projects declare their dependencies, and restoring them is a separate step you run afterwards. That means generation works on an air-gapped machine and its speed does not depend on a package feed.

Performance budgets

These are enforced by the test suite, not aspirations:

ScenarioBudget
5 entities, 5 pages, 5 componentsunder 30 seconds
Name-only manifestunder 10 seconds
Peak working set, any rununder 512 MiB

In practice generation completes in well under a second; the budgets exist as a ceiling that a regression would breach.

These budgets cover generation only

Runtime performance of the generated application — response times, bundle size, Largest Contentful Paint — is not yet enforced. See Limitations.
