Getting started

Installation

The tool needs the .NET 10 SDK and nothing else. Node.js and Playwright browsers matter only when you run the application it generates.

Prerequisites

RequirementVersionNeeded for
.NET SDK 10.0.100 or a later 10.0.1xx feature band Building and running mvp itself. Required.
Node.js + npm ^24.15.0 || >=26.0.0 Installing and serving a generated Angular application. Not needed to generate one.
Playwright browsers installed by npx playwright install Running the generated end-to-end tests. Optional.
Angular CLI any recent version Only the --use-angular-cli opt-in. The default path uses packaged templates.

Confirm the SDK first — look for a 10.x entry:

shell
dotnet --list-sdks

The repository’s global.json pins 10.0.100 with rollForward: latestFeature and allowPrerelease: false, so a later 10.0.1xx SDK is accepted and a preview SDK is not.

Generation is fully offline

Templates are embedded as resources inside the tool. Generating a solution makes no network requests and restores no packages — the generated projects declare their dependencies, and you restore them yourself afterwards.

Option 1 — run from source

The fastest way to try the tool. Nothing is installed onto your machine.

shell
git clone https://github.com/QuinntyneBrown/mvp.git
cd mvp
dotnet restore
dotnet build Mvp.sln --configuration Release
dotnet run --project src/Mvp.Cli -- --help

Everything after -- is passed to the tool. Generating the bundled sample looks like this:

shell
dotnet run --project src/Mvp.Cli -- new dotnet-angular-jwt-mvp --config samples/sample-mvp.yaml --output ./out
output
Generating dotnet-angular-jwt-mvp...
Generated 102 files at '/work/out/Acme'.

The solution lands in ./out/Acme because the sample manifest sets name: Acme. The target directory is always <output>/<Name>.

Option 2 — install as a global tool

shell
dotnet tool install --global Mvp.Cli
mvp --help

The tool is self-contained — Mvp.Core.dll and every template are bundled into the package rather than pulled as a NuGet dependency, so the installed tool works offline.

Prerelease builds

Every commit to main publishes a prerelease, versioned X.Y.Z-preview.N. Install the newest one with:

shell
dotnet tool install --global Mvp.Cli --prerelease
What a prerelease is and is not

A prerelease passes the same cross-platform test matrix and packaged-consumer smoke test as a stable release. It is not release-reviewed, its behaviour can change between builds, and no changelog entry describes it. Use a stable version unless you need something that has not shipped yet.

Update and uninstall

shell
dotnet tool update --global Mvp.Cli
dotnet tool uninstall --global Mvp.Cli

Install to an isolated path instead

Useful when you don’t want the tool on your PATH, or when you want several versions side by side:

shell
dotnet tool install --tool-path ./tool Mvp.Cli
./tool/mvp --help

Install an unreleased local change

To run code that has not been published, pack from a clone and install from that folder. --add-source ./nupkgs is what points NuGet at it:

shell
dotnet pack src/Mvp.Cli --configuration Release --output ./nupkgs
dotnet tool install --global --add-source ./nupkgs Mvp.Cli

Where the global tool lands

PlatformPath
Windows%USERPROFILE%\.dotnet\tools
macOS / Linux~/.dotnet/tools

If mvp is not found after installing, that directory is missing from your PATH. Open a new shell first — the installer prints a note when it has to change your profile.

Updating and uninstalling

dotnet tool install refuses to run when the tool is already installed. Use one of these instead:

shell
# Update in place from the same local source
dotnet tool update --global --add-source ./nupkgs Mvp.Cli

# Or remove it first
dotnet tool uninstall --global Mvp.Cli
Rebuilding is not enough

An installed global tool is a copy. Re-running dotnet pack after a source change does not update it — you must dotnet tool update as well, or you will keep running the old build.

Verify the installation

shell
mvp --version
mvp --help
mvp --version
2.1.0+36ae856375cfd8199b52bf216526436ce97ce818

The suffix after + is the source-revision identifier, so a build always traces back to an exact commit.

mvp --help
Description:
  Create maintainable .NET 10 and Angular 22 MVP solutions.

Usage:
  mvp [command] [options]

Options:
  --diagnostic    Include stack traces and internal details in errors.
  -?, -h, --help  Show help and usage information
  --version       Show version information

Commands:
  new  Generate a solution or one of its constituent projects.

Using the engine without the CLI

If you want to drive generation from your own application rather than a terminal, the engine is a normal NuGet package:

shell
dotnet add package QuinntyneBrown.Mvp.Core

See the Library API page for the entry points.
