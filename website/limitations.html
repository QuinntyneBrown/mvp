Before you commit

Limitations

mvp ships the skeleton and conventions of a working product, not the product. This page is the honest inventory of what it leaves to you — read it before you build on the output.

When to use something else

The tool is opinionated about the stack. It is the wrong choice when you want:

  • A different frontend — Next.js, React, Vue, Svelte, or a mobile application.
  • A different backend — Python, Node.js, Go, or anything that is not .NET 10.
  • To add features to an existing project. Every command creates a new directory; nothing merges into a tree you already have.
  • A different architecture. The layering, MediatR handlers, and library boundaries are fixed by the templates.

Explicitly out of scope

Not providedWhat that means for you
Hosting, deployment, or CI for the generated solution No Dockerfile, no Bicep or Terraform, no pipeline YAML. Deployment is entirely yours to design.
Maintenance of generated code after you modify it Once you edit the output, it is your code. There is no upgrade path that re-applies template changes to a tree you have changed.
Domain breadth beyond what you declare The generator expands exactly the entities, pages, and components in your manifest — and no further.

Not generated in the backend

Only two operations per entity

Each entity gets a create command and a get-by-id query. Update, delete, list, paging, filtering, and sorting are not generated. You get a pattern to copy, not a CRUD surface.

MissingNotes
Refresh-token rotation A RefreshToken entity and its DbSet are generated, but no rotation, issuing, or revocation logic exists. The entity is a placeholder for work you will do.
Sign-in throttling and lockout Nothing rate-limits authentication attempts. Add throttling before exposing the API publicly.
Audit logging No record of who changed what, when.
Security-headers middleware No HSTS, CSP, or frame-options middleware is wired up.
Request logging and observability No structured logging pipeline, no redaction, no tracing, no metrics.
Authorization beyond “authenticated” No roles, claims policies, or per-resource ownership checks.
EF Core migrations EntityFrameworkCore.Design is referenced so you can create them, but none are generated and there is no seeding.
Email flows No confirmation, no password reset, no notifications.

Not generated in the frontend

  • Pages are stubs. A generated page renders a heading; it does not fetch or display your entity data.
  • Components are empty shells with a selector, template, and stylesheet.
  • Only the authentication service is generated in the api library. Typed clients for your own entities are not.
  • No state management beyond the signal-based authentication service.
  • No internationalization, theming system, or design system beyond Angular Material being available as a dependency.

Delivery status

Seventy-seven detailed requirements are tracked. Sixty-nine are implemented; the remaining eight are named below rather than left for you to discover.

69 implemented 5 partial 3 planned

Partial

PartialL2-033

Session termination and expiry handling

Sign-out is available; automatic handling of an expired token during an active session is targeted for a future release.

In practice: when a token expires mid-session, the application does not detect the resulting failures, clear the session, and redirect. Users see requests fail. Handle 401 responses in an interceptor yourself.

PartialL2-040

Library boundary rules

The boundaries exist by construction and are documented; automated enforcement is targeted for a future release.

In practice: nothing stops a developer importing across the intended boundaries. Add a lint rule if the separation matters to your team.

PartialL2-042

Viewport declaration and fluid sizing

The viewport declaration is generated; fluid sizing rules across all generated screens are targeted for a future release.

In practice: the meta tag is present, but generated screens are not systematically built with responsive primitives.

PartialL2-049

Signing key must be replaced before use

A non-functional placeholder ships and replacement is documented; refusal to start with the placeholder value is targeted for a future release.

In practice — this is the one that can hurt you. The generated API will start with REPLACE_WITH_AT_LEAST_32_CHARACTER_RANDOM_SECRET_VALUE as its signing key. Nothing refuses to boot, warns at startup, or fails a health check. Replacing it is entirely a matter of you remembering to.

PartialL2-073

Public API contract and compatibility

The QuinntyneBrown.Mvp.Core package is validated for framework compatibility, but no baselined comparison against a previously published version is enforced, so removal of a public member is not yet caught automatically.

In practice: the supported surface is documented and semantic versioning is followed, but nothing in the build fails when a public member disappears. If you take a dependency on the library, pin the version you tested against.

Planned

PlannedL2-041

Responsive layout across supported viewports

Generated screens are not yet verified usable across the full supported viewport range. Assume you will do layout work for small screens.

PlannedL2-043

Accessibility baseline

Generated screens do not yet meet a stated accessibility baseline. Programmatic labels, keyboard order and focus visibility, contrast ratios, error announcement, and document language and heading structure are all unverified. If you need WCAG 2.1 Level AA, budget for that work — the generated markup is a starting point, not a compliant one.

PlannedL2-059

Runtime performance budgets for generated solutions

No default performance budgets are enforced on the generated application — not response times, not Largest Contentful Paint, not initial bundle size. Generation itself is budgeted; see Output safety.

Partial and planned sit outside the delivery baseline

They are tracked commitments, not promises with dates. Treat everything above as work you own unless and until a release says otherwise.

Operational limits

LimitValue
Manifest file size1 MiB
Supported property typesSeven: string, int, long, decimal, bool, DateTime, Guid. No enums, no collections, no nested types, no relationships.
Entity relationshipsNot expressible. Properties are scalars; foreign keys and navigation properties are yours to add.
Nullability per propertyNot expressible in the manifest.
Frontend librariesFixed at three: api, components, domain.
Custom templatesNot supported. Templates are embedded in the tool and cannot be overridden or extended.
Regeneration into an existing treeNot supported. An existing target is a conflict; --force replaces it wholesale.

Distribution

Most builds you can install are prereleases

Every commit to main publishes an Mvp.Cli prerelease, so the newest installable build is usually one that has had no release review and no changelog entry. Stable versions are cut from a tag and are the ones to depend on; --prerelease is opt-in for a reason.

Security posture

Generated code is a starting point that has not been reviewed for your threat model. Before any non-evaluation use:

  1. Replace Jwt:SigningKey with at least 32 random characters and move it out of source control.
  2. Replace the in-memory store with durable persistence.
  3. Set real allowed origins — the default permits http://localhost:4200 only, which is correct for development and wrong for production.
  4. Add rate limiting, security headers, and audit logging.
  5. Decide your token lifetime and refresh strategy; the default is a 60-minute access token with no refresh flow.
  6. Run your own security review of the whole application.
What the tool does get right

Passwords are hashed with BCrypt at work factor 12. Bearer tokens validate issuer, audience, lifetime, and signing key. CORS names an explicit origin rather than a wildcard. The global exception handler returns no internal detail. Manifest input cannot traverse paths or inject process arguments. These are defaults you should keep.
