Getting started

Quickstart

From nothing to a running application with a working sign-up flow. Generation takes seconds; the slow part is npm install.

This is the sequence CI runs

Every step below is exercised on Windows, Linux, and macOS on each change to the repository, including building the generated backend and frontend. If it breaks, the build goes red.

1. Describe what you want

Save this as mvp.yaml. Every section is optional except name — see the manifest schema for the full contract.

mvp.yaml
name: Acme

entities:
  - name: Project
    properties:
      - name: Title
        type: string
      - name: Description
        type: string
      - name: BudgetCents
        type: long

  - name: Task
    properties:
      - name: Title
        type: string
      - name: IsComplete
        type: bool

pages:
  - name: Projects
    route: projects
    requiresAuth: true
  - name: Settings
    route: settings
    requiresAuth: true

components:
  - name: ProjectCard
    library: domain

This is samples/sample-mvp.yaml from the repository verbatim, so you can point --config straight at it instead.

2. Generate

shell
mvp new dotnet-angular-jwt-mvp --config mvp.yaml --output ./out
output
Generating dotnet-angular-jwt-mvp...
Generated 102 files at '/work/out/Acme'.

102 files: 77 baseline, plus 8 per entity, 3 per page, and 3 per component. Nothing was written until the whole manifest validated. See Generated output for the full inventory.

No manifest? No problem.

mvp new dotnet-angular-jwt-mvp --name Acme --output ./out produces the same 77-file authenticated baseline with no custom entities, pages, or components.

3. Replace the signing key

Do this before anything else. The generated appsettings.json ships a deliberately non-functional placeholder:

out/Acme/backend/src/Acme.Api/appsettings.json
"Jwt": {
  "Issuer": "Acme",
  "Audience": "Acme",
  "SigningKey": "REPLACE_WITH_AT_LEAST_32_CHARACTER_RANDOM_SECRET_VALUE",
  "AccessTokenMinutes": 60
}
The application will still start with the placeholder

Refusing to boot on the placeholder value is a planned behaviour, not a shipped one. Nothing stops you deploying with it, so replacing it is entirely on you. Use at least 32 random characters and keep real secrets out of source control — user secrets, environment variables, or a key vault.

Generate a suitable value:

shell
# PowerShell
[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Max 256 }))

# bash
openssl rand -base64 48

4. Build and run the backend

shell
cd out/Acme/backend
dotnet build
dotnet run --project src/Acme.Api

The API listens on http://localhost:5000 and starts against an in-memory database, so there is nothing to install or migrate. Two endpoints are live immediately:

MethodRouteBodyReturns
POST/api/auth/register{ email, password }AuthResult with a bearer token
POST/api/auth/sign-in{ email, password }AuthResult with a bearer token

Each manifest entity also gets a controller — ProjectController and TaskController here — exposing create and get-by-id.

In-memory data is disposable

The default store is UseInMemoryDatabase. Every restart is a clean slate. To use SQL Server, set ConnectionStrings:Default to a real connection string — that is the only change required; the switch is already wired.

5. Serve the frontend

shell
cd out/Acme/frontend
npm install
npm start

The application serves at http://localhost:4200, which is exactly the origin the generated backend allows through CORS. Sign up, and the auth interceptor attaches the bearer token to every subsequent request while the guard keeps /dashboard and your authenticated pages protected.

Budget a few minutes

npm install typically takes one to three minutes on a first run. Nothing is wrong; the Angular toolchain is large.

6. Run the end-to-end tests

shell
cd out/Acme/frontend
npx playwright install
npm run e2e

npx playwright install downloads browser binaries and is needed once per machine. The generated e2e/tests/auth.spec.ts covers two journeys — a new user registering and reaching the dashboard, and an existing user signing in — using the page-object classes under e2e/pages/. Every page in your manifest gets its own page object, so extending the suite means writing assertions, not scaffolding.

Next steps

  • Add entities, pages, and components to the manifest and regenerate into a fresh directory — see the manifest schema.
  • Read Limitations before you build on this. Only create and get-by-id are generated per entity; update, delete, and list are yours.
  • Configure durable persistence, allowed origins, observability, and deployment before any non-evaluation use.
Regenerating over existing work

Re-running against an existing target exits with code 2 rather than overwriting it. --force replaces it through a recoverable backup — but it replaces the whole tree, including your edits. Generate into a new directory and merge instead.
