# L1 — High-Level Requirements

**Product:** `mvp` — Full-Stack MVP Scaffolding CLI
**Document:** Level 1 Requirements Specification
**Version:** 1.0
**Status:** Baselined
**Audience:** Product stakeholders, adopting engineering teams, integration partners, security reviewers

---

## 1. Purpose

This document states, in plain language, what the `mvp` product must do. It is the highest level of the requirements baseline. Every detailed requirement in `L2.md` traces to exactly one requirement in this document, and every acceptance test written for the product traces to one or more L2 requirements.

## 2. Product Overview

`mvp` is a command-line tool, distributed as a .NET global tool, that generates complete, buildable, JWT-authenticated full-stack web application solutions. A user describes the solution they want — its name, its domain entities, its pages, and its shared components — in a short YAML file. The tool produces a working source tree containing a layered .NET backend, an Angular frontend workspace, and an end-to-end test suite.

The product exists to remove the multi-day setup cost that precedes feature work on a new web application. It delivers architecture, wiring, and conventions; the adopting team delivers the domain.

## 3. Scope

**In scope:** the command-line interface; the declarative manifest format; the generated backend, frontend, and test assets; the security posture of both the tool and its output; the tool's diagnostics, performance, and environment compatibility; and the documentation shipped with the product.

**Out of scope:** hosting, deployment, or continuous-integration infrastructure for generated solutions; ongoing maintenance of generated code after the adopting team modifies it; and domain feature breadth beyond the entities and pages a user declares.

## 4. Definitions

| Term | Meaning |
| --- | --- |
| **Solution** | The complete generated source tree for one application, rooted at a single named directory. |
| **Manifest** | A YAML document describing the solution a user wants generated. |
| **Entity** | A named domain concept with typed properties, persisted by the generated backend. |
| **Page** | A routable screen in the generated frontend application. |
| **Component** | A reusable presentational or domain-aware unit placed in a generated frontend library. |
| **Consumer** | A developer or team that installs `mvp` and uses it to generate a solution. |
| **Generated solution** | The output of a scaffolding run; the artifact the consumer builds upon. |

## 5. Conformance Language

Requirements use **must** and **shall** exclusively. The words *should*, *may*, and *might* do not appear in normative statements. Where a requirement is bounded by a measurable threshold, that threshold appears in the corresponding L2 acceptance criteria.

## 6. Document Status Convention

Each L2 requirement carries a **Status** field:

- **Implemented** — present and verifiable in the current release.
- **Partial** — present in reduced form; the gap is stated in the requirement text.
- **Planned** — specified and baselined; targeted for a future release.

This convention exists so that consumers can distinguish delivered capability from committed capability without reading source code.

# High-Level Requirements

## L1-001: Command-Line Product Surface
The product must present a single, discoverable command-line interface through which every generation capability is invoked. A consumer must be able to learn the full set of available commands, their options, and their purpose without consulting external documentation, and must be able to determine programmatically whether an invocation succeeded.

## L1-002: Distribution and Installation
The product must be distributable and installable as a standard .NET global tool, invocable by a single stable command name from any working directory, on any platform where the supported .NET runtime is available. Installation, verification, and upgrade must each be achievable with documented single-line commands.

## L1-003: Declarative Solution Specification
The product must accept a human-readable, version-controllable declaration of the solution to be generated, covering the solution name, output location, domain entities and their typed properties, application pages and their access requirements, and reusable components and their placement. The declaration must be validated before generation begins, and must remain compatible with later releases of the product.

## L1-004: Full-Stack Solution Generation
The product must generate, from a single command, a complete full-stack solution comprising a layered .NET backend, an Angular frontend workspace, and an end-to-end test suite, organised in a predictable directory layout. Generation must succeed whether the consumer declares a full domain or no domain at all.

## L1-005: Incremental Component Generation
The product must additionally allow a consumer to generate individual parts of a solution — a solution shell, a backend service project, a frontend application, or a frontend library — independently of a full scaffolding run, so that existing work can be extended without regeneration.

## L1-006: Authenticated Access in Generated Applications
Every generated solution must ship a working, end-to-end authentication capability: account registration, credential-based sign-in, issuance of a signed access token, enforcement of that token on protected server endpoints, and client-side session handling that keeps protected screens inaccessible to unauthenticated visitors.

## L1-007: Generated Backend Architecture and Build Integrity
The generated backend must follow a layered architecture with a single, enforced dependency direction, must separate request handling from domain logic, and must compile without errors or warnings-as-errors immediately after generation, with no manual intervention.

## L1-008: Generated Frontend Workspace Structure
The generated frontend must be a single workspace containing one application and a set of clearly bounded libraries, with stable import paths between them, so that presentation, domain, and server-communication concerns remain separable as the application grows.

## L1-009: Responsive and Accessible User Interface
Every screen in the generated frontend must remain usable and legible across the full range of supported viewport sizes, from small mobile displays to large desktop displays, and must meet a defined baseline of accessibility for keyboard operation, assistive technology, and colour contrast.

## L1-010: Automated Acceptance Test Assets
Every generated solution must include a runnable end-to-end test suite structured around the page-object pattern, containing at least one passing test that exercises the authentication path, together with a per-page test scaffold for every page the consumer declared.

## L1-011: Security by Default
Both the tool and every solution it generates must be secure in their default configuration. Credentials must be stored using an accepted one-way hashing function; secrets must never ship as usable values; cross-origin access, input validation, and error disclosure must be restrictive by default; and the tool must not transmit consumer content to any external service.

## L1-012: Data Protection and Persistence Configuration
The generated backend must protect user data at rest and in transit, must default to a persistence mode that is safe for first-run evaluation, must make the transition to a durable database a configuration change rather than a code change, and must never expose or record secret material in responses, logs, or diagnostics.

## L1-013: Performance and Resource Efficiency
The product must complete a scaffolding run within a bounded time on commodity hardware, must not require network access to generate a solution, and must produce solutions whose default runtime behaviour meets stated response-time and load-time budgets.

## L1-014: Diagnostics, Logging, and Error Reporting
The product must report its progress while running, must confirm the location of what it produced on success, and must, on failure, state what failed and what the consumer needs to do about it — without exposing internal implementation detail or secret values.

## L1-015: Environment Compatibility and Graceful Degradation
The product must operate correctly on Windows, macOS, and Linux, must detect the optional third-party tooling it can take advantage of, and must degrade to a documented reduced-capability path rather than failing when that tooling is absent.

## L1-016: Output Safety and Reproducibility
The product must never destroy consumer work without warning, must create the directories it needs, and must produce identical output for identical input, so that generation is a repeatable and reviewable operation.

## L1-017: Product Documentation
The product must ship reference documentation covering the manifest format, the complete inventory of what is generated, a worked example, and the steps a consumer must take after generation before the solution is fit for use beyond local evaluation.
