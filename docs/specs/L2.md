# L2 — Detailed Requirements

**Product:** `mvp` — Full-Stack MVP Scaffolding CLI
**Document:** Level 2 Requirements Specification
**Version:** 2.0
**Status:** Baselined
**Companion document:** `L1.md`

---

## How to Read This Document

Each requirement below is detailed, singular, and testable. Every requirement declares the high-level requirement it satisfies (**Traces to**), its delivery state (**Status**), and a numbered set of acceptance criteria in Given/When/Then form. The acceptance criteria are the contract: two independent engineers reading the same criterion must be able to write the same test.

**Status values:** *Implemented* — present and verifiable in the current release. *Partial* — present in reduced form, with the gap stated. *Planned* — baselined and committed, targeted for a future release.

**Acceptance test convention.** Every acceptance test written against this specification must carry a header comment naming the requirements it covers. This comment is mandatory; it is the mechanism by which coverage of this baseline is verified.

```typescript
// Acceptance Test
// Traces to: L2-027, L2-029
// Description: Registration returns a signed access token carrying the subject claim
```

```csharp
// Acceptance Test
// Traces to: L2-008
// Description: Manifest without a name field fails validation with a non-zero exit code
```

# Detailed Requirements

## L2-001: Root command discovery and help
**Traces to:** L1-001
**Status:** Implemented

The product must expose a root command that describes the product's purpose and lists its available command groups. Help must be available at every level of the command tree.

**Acceptance Criteria:**
1. Given the tool is installed, when the consumer runs `mvp --help`, then the output states the product's purpose and lists `new` as an available command.
2. Given the tool is installed, when the consumer runs `mvp new --help`, then the output lists every generation subcommand with a one-line description of each.
3. Given any subcommand, when the consumer appends `--help`, then the output lists every option that subcommand accepts, each with a description and its aliases.
4. Given the consumer supplies an unrecognised command or option, when the tool runs, then it reports the unrecognised input and exits with a non-zero status.

---

## L2-002: Generation commands grouped under a single verb
**Traces to:** L1-001
**Status:** Implemented

All generation capabilities must be reachable under one grouping verb, so that the command surface remains predictable as capabilities are added.

**Acceptance Criteria:**
1. Given the tool is installed, when the consumer lists the subcommands of `new`, then the set contains exactly: `solution`, `api`, `core`, `infrastructure`, `app`, `api-library`, `components-library`, `domain-library`, and `dotnet-angular-jwt-mvp`.
2. Given a new generation capability is added to the product, when the consumer lists the subcommands of `new`, then the new capability appears in that list with a description.

---

## L2-003: Deterministic exit codes
**Traces to:** L1-001
**Status:** Implemented

The product must communicate outcome through its process exit code so that it can be used safely in scripts and automated pipelines.

**Acceptance Criteria:**
1. Given a valid invocation, when generation completes without error, then the process exits with status `0`.
2. Given invalid syntax, an unreadable manifest, or failed validation, when the tool terminates, then it exits with status `1`.
3. Given an existing target without `--force`, when the tool terminates, then it exits with status `2`.
4. Given a generation or external-tool failure, when the tool terminates, then it exits with status `3`.
5. Given an unexpected internal failure, when the tool terminates, then it exits with status `70`.
6. Given cancellation, when the tool terminates, then it exits with status `130`.
7. Given the tool exits with a non-zero status, when the consumer inspects standard error, then a message describing the failure is present.

## L2-004: Consistent option naming across commands
**Traces to:** L1-001
**Status:** Implemented

Options that carry the same meaning must be named and abbreviated identically across every command.

**Acceptance Criteria:**
1. Given any generation command that accepts a solution or project name, when the consumer inspects its help output, then the option is named `--name` with alias `-n`.
2. Given any generation command that accepts an output location, when the consumer inspects its help output, then the option is named `--output` with alias `-o`.
3. Given any generation command that accepts a manifest, when the consumer inspects its help output, then the option is named `--config` with alias `-c`.
4. Given a command whose `--output` option is omitted, when the command runs, then the current working directory is used as the output location.

## L2-005: Global tool packaging and invocation name
**Traces to:** L1-002
**Status:** Implemented

The product must be packaged as a .NET global tool that installs a single stable executable command.

**Acceptance Criteria:**
1. Given the package is installed with `dotnet tool install -g`, when the consumer opens a new shell in any directory, then the command `mvp` is resolvable and executes the product.
2. Given the tool is already installed, when the consumer runs `dotnet tool update -g`, then the installed version is replaced by the newer version and the command name is unchanged.
3. Given the tool is installed, when the consumer runs `dotnet tool uninstall -g`, then the `mvp` command is no longer resolvable.

## L2-006: Runtime prerequisite declaration
**Traces to:** L1-002
**Status:** Implemented

The product must declare its runtime prerequisite and must fail with an intelligible message rather than an unhandled error when that prerequisite is unmet.

**Acceptance Criteria:**
1. Given a machine with the .NET 10 SDK or runtime present, when the consumer installs and runs the tool, then installation and execution succeed.
2. Given a machine whose highest installed .NET runtime is below the supported major version, when the consumer attempts installation, then the installer reports the required version.
3. Given the product documentation, when a consumer reads the prerequisites section, then the required SDK version and the verification command are stated explicitly.

## L2-007: Manifest format and field naming
**Traces to:** L1-003
**Status:** Implemented

The solution declaration must be a YAML document using camelCase field names, readable and editable without tooling and safe to store in version control.

**Acceptance Criteria:**
1. Given a UTF-8 YAML file whose fields use camelCase naming, when the tool loads it, then every declared field is bound to the corresponding manifest value.
2. Given a manifest file that is not well-formed YAML, when the tool loads it, then the tool reports a parse failure identifying the manifest path and exits with a non-zero status.
3. Given a manifest file that is empty, when the tool loads it, then the tool reports that the manifest is empty or invalid and exits with a non-zero status.
4. Given a manifest larger than 1 MiB, when the tool loads it, then it reports the size limit and exits before generation.

## L2-008: Solution name is required and validated
**Traces to:** L1-003
**Status:** Implemented

A solution name must be supplied before generation proceeds, because it determines the solution directory, the namespace root, and the frontend workspace prefix.

**Acceptance Criteria:**
1. Given a manifest containing a non-empty `name`, when generation runs, then that value is used as the solution name.
2. Given a manifest whose `name` field is absent, empty, or whitespace, and no `--name` option is supplied, when the tool runs, then it reports that a solution name is required, names both ways of supplying it, and exits with a non-zero status.
3. Given no manifest and no `--name` option, when the tool runs, then it reports that a solution name is required and exits with a non-zero status.
4. Given any solution, entity, property, page, component, or incremental name, when it is not an ASCII PascalCase identifier or is reserved, then validation reports every violation before writing output.

## L2-009: Entity and property declaration
**Traces to:** L1-003
**Status:** Implemented

The manifest must allow zero or more domain entities, each with zero or more typed properties, and must generate persistence, application, and interface artifacts from each.

**Acceptance Criteria:**
1. Given a manifest entity with a `name` and a list of properties each having `name` and `type`, when generation runs, then a domain class carrying every declared property with the declared type is produced.
2. Given an entity property whose `type` is omitted, when generation runs, then the property is generated with type `string`.
3. Given any generated entity, when the consumer inspects the domain class, then an identifier property and a creation-timestamp property are present without having been declared in the manifest.
4. Given a property whose declared type is one of `string`, `int`, `long`, `decimal`, `bool`, `DateTime`, or `Guid`, when generation runs, then the generated code compiles without error.
5. Given a manifest with no `entities` list, when generation runs, then generation completes successfully and no entity-specific artifacts are produced.
6. Given duplicate entity or property names, or a property type outside the exact supported set, when validation runs, then all such errors are reported and generation does not begin.

## L2-010: Page declaration with route and access defaults
**Traces to:** L1-003
**Status:** Implemented

The manifest must allow zero or more application pages, each with an optional route and an access requirement that defaults to authenticated.

**Acceptance Criteria:**
1. Given a page declaration with `name` and `route`, when generation runs, then a routable screen is produced and registered at the declared route.
2. Given a page declaration whose `route` is omitted, when generation runs, then the route is the kebab-cased form of the page name.
3. Given a page declaration whose `requiresAuth` is omitted, when generation runs, then the page is registered behind the authentication guard.
4. Given a page declaration with `requiresAuth: false`, when generation runs, then the page is reachable without an authenticated session.
5. Given an explicit route, when it is not composed of lower-case kebab-case path segments, then validation fails before generation.

## L2-011: Component declaration and library placement
**Traces to:** L1-003
**Status:** Implemented

The manifest must allow zero or more reusable components, each assigned to a named frontend library.

**Acceptance Criteria:**
1. Given a component declaration with `name` and `library: components`, when generation runs, then a component unit is produced within the presentational library.
2. Given a component declaration with `name` and `library: domain`, when generation runs, then a component unit is produced within the domain library.
3. Given a component declaration whose `library` is omitted, when generation runs, then the component is placed in the presentational library.
4. Given a component declaration naming a library that does not exist, when generation runs, then the tool reports the unsupported library name and exits with a non-zero status.
5. Given a component declaration with `library: api`, when generation runs, then a standalone component unit is produced and exported by the API library.

## L2-012: Forward compatibility of the manifest
**Traces to:** L1-003
**Status:** Implemented

A manifest authored against one release must remain loadable by later releases, and unknown fields must not halt generation.

**Acceptance Criteria:**
1. Given a manifest containing a field the current release does not recognise, when the tool loads it, then the unrecognised field is ignored and generation proceeds using the recognised fields.
2. Given a manifest containing an unrecognised field, when it is loaded, then a warning identifies the ignored field.
3. Given a manifest authored against an earlier release, when a later release loads it, then every field valid in the earlier release is honoured.
4. Given the product documentation, when a consumer reads the manifest reference, then it states that unrecognised fields are ignored with a warning and that field names must therefore be verified against the reference.

## L2-013: Input precedence and output resolution
**Traces to:** L1-003
**Status:** Implemented

Where the same value can be supplied by more than one channel, precedence must be defined and documented.

**Acceptance Criteria:**
1. Given both a manifest `name` and a `--name` option, when generation runs, then the `--name` value is used.
2. Given a `--output` option, a manifest `output` field, and a current working directory, when generation runs, then the `--output` value is used.
3. Given no `--output` option but a manifest `output` field, when generation runs, then the manifest value is used.
4. Given neither a `--output` option nor a manifest `output` field, when generation runs, then the current working directory is used.
5. Given a resolved output location, when generation runs, then the solution is created in a subdirectory of that location named after the solution.

## L2-014: Missing or unreadable manifest handling
**Traces to:** L1-003
**Status:** Implemented

A manifest path that cannot be read must produce a clear, actionable failure rather than an unhandled error.

**Acceptance Criteria:**
1. Given a `--config` path that does not exist, when the tool runs, then it reports that the manifest file was not found, includes the supplied path in the message, and exits with a non-zero status.
2. Given a `--config` path that exists but cannot be read due to permissions, when the tool runs, then it reports the access failure and exits with a non-zero status.
3. Given any manifest failure, when the tool terminates, then no partial solution directory is left in a state the consumer would mistake for a successful run.

## L2-015: The manifest is data, never executable input
**Traces to:** L1-003
**Status:** Implemented

The manifest must be treated strictly as data. No content within a manifest may cause the tool to execute arbitrary code, resolve arbitrary types, or read files outside the declared inputs.

**Acceptance Criteria:**
1. Given a manifest containing YAML type tags that name arbitrary types, when the tool loads it, then no type outside the manifest's own schema is instantiated.
2. Given a manifest field whose value contains shell metacharacters, when generation runs, then the value is treated as literal text and no shell command is constructed from it.
3. Given a manifest field whose value contains directory-traversal sequences, when generation runs, then no file is written outside the resolved output directory.

## L2-016: Full-stack generation from a single command
**Traces to:** L1-004
**Status:** Implemented

One command must produce the complete solution, laid out in a documented and predictable directory structure.

**Acceptance Criteria:**
1. Given a valid manifest and output location, when the consumer runs the full-stack generation command, then a directory named after the solution is created in the output location.
2. Given a completed generation run, when the consumer inspects the solution directory, then it contains a backend directory and a frontend directory at the top level.
3. Given a completed generation run, when the consumer inspects the backend directory, then it contains a solution file and four projects named for the domain, application, infrastructure, and interface layers of the solution.
4. Given a completed generation run, when the consumer inspects the frontend directory, then it contains a workspace configuration, an application project, three library projects, and an end-to-end test directory.

## L2-018: Per-entity artifact generation
**Traces to:** L1-004
**Status:** Implemented

Each declared entity must produce a complete vertical slice across the backend layers so that the consumer can create and retrieve instances of it without writing code.

**Acceptance Criteria:**
1. Given a declared entity, when generation runs, then a domain class, a creation command with its handler and validator, a retrieval query with its handler, a data-transfer object, and an interface endpoint set are all produced for that entity.

3. Given a generated entity endpoint set, when an authenticated client requests an entity by an identifier that exists, then the entity's data-transfer representation is returned.
4. Given a generated entity endpoint set, when an unauthenticated client calls any of its endpoints, then the response status is `401 Unauthorized`.
5. Given an entity whose name collides with a reserved framework type name, when generation runs, then the generated code fully qualifies the framework type and compiles without error.

## L2-027: Account registration
**Traces to:** L1-006
**Status:** Implemented

The generated backend must accept a registration request and create an account for a previously unregistered email address.

**Acceptance Criteria:**
1. Given no account exists for an email address, when a client submits a registration request with that email, a display name, and a password satisfying the password policy, then the account is created and an authentication result containing an access token is returned.
2. Given an account already exists for an email address, when a client submits a registration request with that email, then the response status is `400 Bad Request` and the body states that the email is already registered.
3. Given a registration request whose email is malformed, missing, or whose password violates the password policy, when the request is processed, then the response status is `400 Bad Request` and the body lists the failing fields.
4. Given any registration response, when the consumer inspects the body, then no password value and no password hash are present.

## L2-028: Credential-based sign-in
**Traces to:** L1-006
**Status:** Implemented

The generated backend must exchange valid credentials for an access token and must reject invalid credentials without disclosing which element was wrong.

**Acceptance Criteria:**
1. Given a registered account, when a client submits a sign-in request with the correct email and password, then an authentication result containing an access token and its expiry is returned.
2. Given a registered account, when a client submits a sign-in request with an incorrect password, then the response status is `400 Bad Request` and the message does not indicate whether the email or the password was incorrect.
3. Given no account exists for an email address, when a client submits a sign-in request with that email, then the response is indistinguishable in status and message from the incorrect-password response.

## L2-029: Access token issuance and claims
**Traces to:** L1-006
**Status:** Implemented

Issued access tokens must be signed, time-limited, and must carry the claims the application needs to identify and authorise the caller.

**Acceptance Criteria:**
1. Given a successful registration or sign-in, when the issued token is inspected, then it is signed with the HMAC-SHA256 algorithm using the configured signing key.
2. Given an issued token, when its claims are inspected, then a subject claim carrying the account identifier, an email claim, a display-name claim, a role claim, and a unique token identifier claim are all present.
3. Given an issued token, when its lifetime is inspected, then the expiry is the issue time plus the configured access-token lifetime, and the default configured lifetime is 60 minutes.
4. Given an issued token, when its payload is inspected, then no password, password hash, or signing key material is present.

---

## L2-030: Token validation on protected endpoints
**Traces to:** L1-006
**Status:** Implemented

Protected endpoints must accept only tokens that pass full validation.

**Acceptance Criteria:**
1. Given a protected endpoint, when a request arrives with a valid, unexpired token issued by the configured issuer for the configured audience, then the request is processed.
2. Given a protected endpoint, when a request arrives with no token, then the response status is `401 Unauthorized`.
3. Given a protected endpoint, when a request arrives with a token whose signature is invalid, whose issuer or audience does not match configuration, or whose lifetime has elapsed, then the response status is `401 Unauthorized`.
4. Given the configured token validation, when it is inspected, then issuer, audience, lifetime, and signing-key validation are all enabled and the permitted clock skew is at most 30 seconds.

## L2-031: Client session persistence and token attachment
**Traces to:** L1-006
**Status:** Implemented

The generated frontend must retain the authenticated session across page reloads and must attach the access token to requests it makes to the generated backend.

**Acceptance Criteria:**
1. Given a visitor signs in successfully, when the browser is reloaded, then the visitor remains signed in.
2. Given an authenticated session, when the application issues a request to the backend, then the request carries the access token in an `Authorization: Bearer` header.
3. Given no authenticated session, when the application issues a request to the backend, then no `Authorization` header is attached.
4. Given an authenticated session, when the application issues a request to a host other than the configured backend, then no access token is attached to that request.

---

## L2-032: Route guarding and redirection
**Traces to:** L1-006
**Status:** Implemented

Screens that require authentication must be unreachable without a session, and the visitor must be routed somewhere useful rather than shown an error.

**Acceptance Criteria:**
1. Given no authenticated session, when a visitor navigates to a guarded route, then the visitor is redirected to the sign-in screen and the guarded screen does not render.
2. Given an authenticated session, when a visitor navigates to a guarded route, then the guarded screen renders.
3. Given an authenticated session, when a visitor navigates to the sign-in or sign-up screen, then the visitor is routed to the dashboard.

---

## L2-033: Session termination and expiry handling
**Traces to:** L1-006
**Status:** Partial — sign-out is available; automatic handling of an expired token during an active session is targeted for a future release.

The generated frontend must allow a visitor to end their session deliberately, and must handle an expired session without stranding the visitor.

**Acceptance Criteria:**
1. Given an authenticated session, when the visitor signs out, then the stored session is cleared and the visitor is routed to the sign-in screen.
2. Given a signed-out visitor, when the browser is reloaded, then no authenticated session is restored.
3. Given an authenticated session whose token has expired, when the application receives a `401 Unauthorized` response from the backend, then the stored session is cleared and the visitor is routed to the sign-in screen.

## L2-034: Layered architecture and dependency direction
**Traces to:** L1-007
**Status:** Implemented

The generated backend must separate domain, application, infrastructure, and interface concerns, with dependencies pointing inward only.

**Acceptance Criteria:**
1. Given the generated backend, when project references are inspected, then the domain project references no other project in the solution.
2. Given the generated backend, when project references are inspected, then the application project references only the domain project.
3. Given the generated backend, when project references are inspected, then the infrastructure and interface projects reference the application project, and the application project references neither of them.
4. Given the generated application layer, when its abstractions are inspected, then persistence, clock, current-user, token-issuing, and password-hashing capabilities are expressed as interfaces implemented in the infrastructure layer.

## L2-036: Request validation pipeline
**Traces to:** L1-007
**Status:** Implemented

Every command that enters the application layer must be validated before its handler executes, without each handler restating validation logic.

**Acceptance Criteria:**
1. Given a command with an associated validator, when the command is dispatched with input that violates a rule, then the handler does not execute and a validation failure is raised.

## L2-037: Consistent error contract
**Traces to:** L1-007
**Status:** Implemented

The generated backend must return a consistent, predictable error shape and must never surface internal detail to a caller.

**Acceptance Criteria:**
1. Given a validation failure, when the response is returned, then it carries a title identifying the failure category and a collection of field-level errors.
2. Given a known domain failure such as duplicate registration or invalid credentials, when the response is returned, then the status is `400 Bad Request` and the body carries a title describing the failure.
3. Given an unhandled exception, when the response is returned, then the status is `500 Internal Server Error` and the body carries a generic message containing no exception type, message, or stack trace.

## L2-039: Application bootstrap and configuration
**Traces to:** L1-008
**Status:** Implemented

The generated application must bootstrap through a single, inspectable configuration that registers routing, network access, animation, and authentication services.

**Acceptance Criteria:**
